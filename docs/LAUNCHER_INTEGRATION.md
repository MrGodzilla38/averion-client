# Averion Launcher integration

This is a proposed contract between separate repositories. Averion Launcher owns Minecraft, Java runtime, Fabric profiles, downloads, managed dependencies and per-profile installation. The client owns its configuration and runtime features. Build and release outputs contain a client mod jar.

## Discovery and selection

Use the configured `MrGodzilla38/averion-client` repository as the initial authority for GitHub Releases. List published releases with pagination and conditional requests, find the manifest and signing bundle by asset name, and verify them before selection. Ignore drafts. Match GitHub tag and prerelease status to the signed version and channel. Use signed sequence to order releases within a channel. The preview channel is explicit opt-in and maintains its own sequence. A different channel is an explicit profile choice. A newer release missing the selected game version leaves an existing installation usable and offers the newest eligible verified build for that game. If no eligible target exists, show Averion as unavailable for the selected version. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases).

## Manifest v1

Each release attaches `averion-client-manifest-v1.json` and `averion-client-manifest-v1.sigstore.json`. The [schema](../distribution/manifest-v1.schema.json) and [synthetic example](../distribution/manifest-v1.example.json) describe the wire format. The tag is `v<clientVersion>`. Use SemVer without build metadata. Stable versions have no prerelease suffix. Preview versions require one. `sequence` increases within each channel, independent of SemVer ordering. Each target contains the exact Mojang game ID, JRE major, exact stable tested Loader version, Averion file and exact required dependencies. CI and publishing must compare target fields to the jar metadata and verify every declared dependency. The canonical artifact name is `averion-client-<minecraftVersion>.jar`. Dependencies are keyed by Fabric mod ID and reference an exact upstream Modrinth project/version and file identity. The Launcher validates upstream identity, game version, Fabric and SHA-512, plus the publisher-signed SHA-256 and byte count. If no runtime dependencies are needed, the array is empty.

Asset URLs include the release tag and end with the canonical filename. For example, release `v0.1.0` uses `/releases/download/v0.1.0/averion-client-1.16.5.jar`. The same filename can appear in multiple releases. Identify a build by the signed `clientVersion` and `minecraftVersion` pair, verify the jar's mod version and Minecraft dependency against that pair, and include the signed SHA-256 in cache and inventory identity. A staged update can replace an older managed jar at the same destination filename. The example uses placeholder sizes and hashes for Averion jars.

The launcher rejects duplicate JSON keys, game IDs, dependency IDs and destination paths, and validates the schema, tag/channel consistency, canonical artifact name derived from the exact Minecraft ID, release tag and filename in the asset URL, URL policy and integer bounds. Publication includes a complete resolved closure of required dependencies for each target. Manifest v1 allows additive targets and new releases. Changes to required fields, semantics, URL policies or supported providers require a new schema version and launcher support. Unsupported versions are ineligible.

Some early Fabric API releases have a literal `%2B` in the filename reported by Modrinth. Dependency names allow this sequence and preserve it for upstream identity checks and local filenames.

## Install, update and roll back

1. Select the exact Minecraft target and channel and authenticate the manifest. Resolve its pinned stable Loader through Fabric Meta for that Minecraft version, obtain the matching profile and declared Java major, and use upstream game and runtime sources. Fail if any pinned requirement is unavailable. [Fabric Meta](https://meta.fabricmc.net/).
2. Under a profile lock held across preparation and commit, build a prospective managed inventory. Stage downloads on the same filesystem as the destination. Verify every file and cross-check mod IDs, runtime constraints, installed user conflicts and dependency closure. Protect unrelated and altered user files. Pause the transaction if a user mod occupies a required slot. A known valid duplicate can satisfy a dependency in place with its ownership preserved.
3. Require the game process to be stopped for commit. Write a durable journal covering old inventory, staged files and replacement paths. Atomically rename individual staged files into place and publish the updated inventory last. A multi-file install is a transaction enforced by the launcher lock, journal and recovery before every launch. Flush files and directory changes where the platform supports it. Recover by restoring the prior inventory and files or completing the verified transaction. Keep owned-file backups and reverify them for rollback. Persist the signed manifest and verification state with the generation.
4. Start Minecraft with the isolated game directory, Fabric profile and validated Java. Launch an existing verified generation while offline when all files and authorized game/account prerequisites are locally available. If a download is interrupted, retain the prior generation. Retry from staging, verifying the full completed file even if a validated range resume is used. Re-fetch corrupt files under a bounded retry policy.
5. Rollback is a deliberate selection of a cached authenticated compatible generation, with its exact Loader and dependencies. Keep update high-water marks while rolling back. Preserve saves, options, user mods and client settings. A game downgrade may be incompatible with upgraded worlds and settings. Keep game versions in isolated profiles and treat world conversion separately.

Inventory entries record Fabric ID, source and upstream identifiers, installed filename, hash and owner. Delete a retired file only when the inventory marks it as launcher-managed and the installed hash still matches. Recover referenced generations after interrupted operations before pruning. See [Security and distribution](SECURITY_AND_DISTRIBUTION.md).
